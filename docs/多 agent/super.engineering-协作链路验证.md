# super.engineering 协作链路验证

- 日期：2026-10-30
- 状态：第一阶段通过；真实代码交付尚未验证
- 范围：当前应用持续运行期间的文本协作，不代表长期可靠性

## 用户目标

需求方案由用户确认，随后主 Agent 自动分工、管理 worktree、安排跨模型评审、修复、测试和集成。最终只合入功能集成分支，不合入 main。允许符合需求与整体架构的调整，调整记录随最终代码交付。

## 实验与证据

使用应用支持的 sc 命令，无额外编排程序。作者为 Claude provider，评审者为 Codex provider，均使用结构化聊天会话。未指定或核验具体模型版本，故本轮直接证明的是跨 provider 会话交接。

| 步骤 | 可定位的会话 | 观察结果 |
|---|---|---|
| 作者生成流程草案 | sdlc-probe-author | 完成后应用发送通知，主会话继续读取结果 |
| 独立评审 | sdlc-probe-reviewer | 返回 request_changes，指出提交绑定、集成验证和失败预算问题 |
| 交回原作者修订 | sdlc-probe-author | send 接受消息，原会话继续执行并完成修订 |
| 复审 | sdlc-probe-reviewer | 返回 approve，确认三项问题已解决 |

四次完成通知均触发主会话后续处理，期间未要求用户手动输入“继续”。结果读取均返回结构化完整内容。评审提示明确要求检查提交绑定和组合代码验证，因此不以本轮结果衡量模型自主发现缺陷的能力。

这是合成文本实验。作者和评审者未执行代码、修改文件或创建 worktree。主会话仅在实验结束后新增本记录，原方案保持不变。未提交或合并代码。

## 已证实与未证实

已证实：跨 provider 启动、完成通知、主会话继续、完整结果读取、原会话返工、复审与终止。

未证实：具体模型身份、独立 worktree 开发与评审、真实测试失败修复、合并冲突处理、自动集成、执行记录完整性、进程故障及应用重启恢复、多轮长期稳定性。

## 官方本机指南中的限制

依据 sc instructions orchestration 与 sc instructions worktree：

- team run 支持并行汇总，本身不提供顺序工作流。
- 应用重启不会自动恢复未完成的 team run 角色；本轮未实际重启应用。
- 任务型 worktree 启动的子会话，在收到人类输入前不能再为该任务创建 worktree。因此后续实验应由原主会话集中管理开发与评审 worktree。
- 创建 worktree 或分支需要用户明确提出，不能从普通任务或隔离需要中推断授权。

## 下一阶段建议

在明确授权的实验分支和 worktree 中，选择符合本仓库范围的小型真实变更：两个开发任务、独立评审、至少一次失败修复、最终集成测试。记录开发及评审实际模型、候选提交、基线提交、最终集成提交、测试证据与调整理由。只更新实验集成分支，不更新 main。

当前结论：已有协作机制值得继续验证，尚无理由为消息派发与结果回收自建 orch；也尚不能宣称满足无人值守代码交付。
