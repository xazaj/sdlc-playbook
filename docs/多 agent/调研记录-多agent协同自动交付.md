## 1. 调研目的（真实诉求）

### 1.1 触发背景

原始设计稿提出了一套本地多 Agent 协同方案：以 Claude Code 为主 Agent，用 Beads 管任务图、SQLite 管执行态、worker 在独立 worktree 里跑，推荐先落地一个裁剪版 v0。但该方案对"如何建一个多 Agent 执行系统"考虑得很细，对"为什么需要这个系统"确认不足，直接实现 v0 可能过早。

### 1.2 通过三轮问答确认的真实诉求

诉求分两个阶段，参与方式不同：

| 阶段 | 用户参与方式 | 系统应承担 |
|---|---|---|
| 需求与方案 | 持续参与，最终拍板 | 多模型评审、汇总分歧、组织修订 |
| 开发与交付 | 确认方案后离开，最后验收 | 分工、worktree 管理、开发、交叉评审、修复、测试、合并 |

最终明确的一句话诉求：

> 用户参与需求与方案确认；确认后，主 Agent 自主组织多模型开发、评审、修复、测试与集成，将代码合入功能集成分支，并交付完整的调整记录，供用户最终验收。不自动合入 main。

三条补充边界：

1. **自动合并终点**：子任务合入功能集成分支；不自动合入 main。
2. **自主调整范围**：允许符合需求目标、符合项目整体架构的调整，但调整必须记录，随最终代码一起交付。
3. **首要改善项**：少操心。进入开发阶段后不想盯屏幕，希望自动化完成。

### 1.3 诉求拆解（对方案评估的影响）

真正的验收标准是：

> 用户确认方案后不再发送"继续"、不再搬运评审意见、不再手工协调合并，系统仍能完成一个真实功能，并给出足够的证据供验收。

据此，"使用多模型"和"worktree 隔离"都是实现手段，不是目的；要减少的是用户承担的协调工作，以及"必须等用户回复才能继续"的次数。

## 3. 调研过程与结果

调研分五个阶段，每阶段有明确结论。

### 3.1 阶段一：评估原方案是否匹配真实诉求

结论：原方案方向部分正确，但**推荐先落地的 v0 不符合核心诉求**。

v0 恰好裁掉了用户最需要的能力：独立 reviewer、自动修复重试、自动合并、遇问题持续推进的机制。原稿没有把"由主 Agent 连续自主完成、不等人输入"作为首要验收条件。

完整方案更接近目标，但有三个偏差：

1. 把省主 Agent token 放在首位，而用户更愿意用合理成本换取少操心。
2. 扩展能力过多：多机、看板镜像、四家适配器、日预算账本，均未从真实痛点中得到必要性证明。
3. 执行流程写得多，判断与返工闭环写得少：真正决定能否离开屏幕的是"评审不通过怎么办、评审意见冲突怎么办、集成失败怎么办、谁持续负责解决"。

原方案最大的问题：

> 它按"少实现几个组件"来定义最小方案，而用户需要按"少覆盖一些场景，但完整自动交付"来定义最小方案。

风险定性：**存在做了不该做的事的风险**——为了让用户不盯开发过程，先让用户承担一个通用编排平台的建设和维护。下一步应先验证现有工具能否完成自动交付流程，再决定补什么能力，而不是先选 Beads、SQLite 或 daemon。

### 3.2 阶段二：调研现有工具

先查官方仓库与工作流文档，再核对本机 super.engineering 指南。四个候选结论：

| 候选 | 对诉求的价值 | 尚存缺口 | 判断 |
|---|---|---|---|
| super.engineering | 已在用；支持跨模型交接、完成通知、worktree 管理 | 完整闭环需组织；重启恢复有限 | 先做最低成本验证 |
| Orchestrator.inc | 独立 reviewer、评审意见回传、CI 失败回传 | 自动评审不等于自动合并，主要围绕 PR | 重点备选 |
| Gas Town | 持久任务、监控恢复、集成分支、合并队列较完整 | 组件多；跨模型评审门禁仍需验证 | 偏完整自动化的候选 |
| CAO | 多步骤、分支、循环工作流，执行日志与恢复 | 仍需编写交付流程代码，承担维护 | 需要精确流程控制时考虑 |

关键发现：现有工具中，有的只管理多个会话，有的会把测试失败、评审意见和合并冲突自动交回开发 Agent，后者更接近诉求。

对原方案的判断：**用户需要补充的是项目交付规则，执行基础设施应尽量复用**。应保留的规则（方案确认后的自主范围、开发者与评审者不同模型、评审绑定具体提交、失败处理流程、只合功能集成分支、调整记录随交付）；暂时不必自建的（四家适配器、消息总线、看板镜像、任务与执行双账本）。这符合本仓库"已有资产够用就编排，不重复建设"的定位。

### 3.3 阶段三：super.engineering 协作链路验证（文本实验）

用不修改文件的受控实验验证"起草 → 独立评审 → 返工 → 复审"链路。

结果：**通过**。

- Claude、Codex 会话均成功启动，结果可完整读取。
- 四次完成通知均让主会话继续执行，无需用户输入"继续"。
- Codex 首轮要求修订三项（评审与测试绑定提交、验证最终集成结果、明确失败重试上限），Claude 修订后 Codex 复审通过。

限制：这是合成文本实验，未执行代码、修改文件或创建 worktree，只证明了跨 provider 协作链路可用，不代表真实代码交付能力。

### 3.4 阶段四：真实代码交付实验

经用户明确授权，创建实验集成分支和开发/评审 worktree，用一个小型真实变更验证。

变更：修复站点 prompt 提取器——提取器只识别四个及以上反引号，而正文契约接受三个及以上，二者不一致。

结果：**开发、评审、集成通过；无人值守失败**。

| 环节 | 结果 |
|---|---|
| 开发 | Claude 完成提交 `ce6985e`，21 项测试通过 |
| 独立评审 | Codex（gpt-6-luna / low）绑定提交评审，approve，独立跑通 21 项测试 |
| 集成复验 | 主会话复跑 21 项测试与站点构建，构建成功生成 72 页 |
| 合并 | 合入实验集成分支，提交 `821e1de` |
| 边界 | 未合入 main（main 仍为 `bba4d5f`），未推送 |

**关键失败**：任务型 worktree 的开发任务完成后，主协调者没有自动继续，用户提醒后才安排评审。因此**无人值守这一项判为失败**，不能以文本实验的同 worktree 通知成功来代替。

### 3.5 阶段五：排查无人值守断点

用户要求查清断点。排查过程中发现并逐步纠正了几个判断：

1. **父会话关联差异**：此前能自动唤醒主会话的聊天 Agent 都有明确的父会话关联；通过 `sc worktree create` 启动的开发/评审会话没有这个关联。初始假设是"创建 worktree 任务不等于建立完成通知"。
2. **send 返回成功不代表已执行**：跨 worktree 发送探针时，`sc agent send` 首次返回成功，但实际只是文本已粘贴进 Codex 终端、尚未提交执行。`sc agent wait` 返回 `prompt_stalled`，终端快照确认探针仍留在输入框里。
3. **需要显式提交输入**：用 `sc terminal input --key Enter` 提交已确认的输入后，任务才真正开始执行，`sc agent wait` 随后返回成功。

当前状态：已定位到"跨 worktree 会话无父会话关联 + 输入需要显式提交"是续接不可靠的可疑根因，正在用低成本模型（Haiku）做最小复现实验验证显式等待路径。尚未确认能否可靠解决，也尚未宣布无人值守通过。

### 3.6 阶段六：调研 herdr 能否替代 sc 并降低 token 消耗

用户反馈 sc 特别消耗 token，要求调研 herdr 是否能完成同一目标，以及 herdr 的最佳实践。调研依据：本机 herdr 0.9.5 实测、官方 skill、agent-automation / agents / session-state / plugins / socket-api 文档。

herdr 是什么：terminal workspace manager（multiplexer + agent 识别），把 workspace/tab/pane 拓扑、原始终端控制、agent 生命周期状态三类原语暴露给 CLI 和 socket API。它本身**不是编排器**，不提供任务图、账本、自动重试、自动合并。

与 sc 的关键差异（针对两个痛点）：

| 维度 | super.engineering (sc) | herdr |
|---|---|---|
| 等待模型 | 异步：派发 → 结束回合 → 等系统通知（依赖父会话关联） | 同步阻塞：`agent prompt --wait` 派发并阻塞等待 |
| 跨 worktree 断点 | 无父会话关联 → 完成不通知 → 停住 | 无此断点：主 Agent 自己阻塞等，不依赖系统通知 |
| 等待期间 token | 结束回合等通知；恢复回合要重新读状态 | 0 token，阻塞在系统调用上 |
| 读取结果 | `--output json` 返回完整结构化结果 | `agent read --lines N`（默认 80 行）精确控制 |
| 结果回收 | 完整 JSON | 官方推荐 worker 写文件、只回传路径（信封模式） |

省 token 的三个机制（均来自官方文档）：

1. `agent prompt --wait --timeout` 阻塞等待，等待期间不消耗主 Agent token。
2. `agent read --lines N` 默认 80 行，读取量可控。
3. 官方 fallback：让 worker 把结果写成 Markdown 文件、只回复文件路径，主 Agent 读文件而非 transcript——即原方案的信封模式。

官方最佳实践 recipe（agent-automation）：

```bash
split=$(herdr pane split --current --direction right --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
herdr agent start reviewer --kind codex --pane "$review_pane" -- -m gpt-5.4
herdr agent prompt reviewer "Review the current diff" --wait --timeout 120000
herdr agent read reviewer --source recent-unwrapped --lines 120
```

已支持 26 种 agent kind（pi/claude/codex/gemini/omp/opencode 等），`herdr worktree create --branch --base` 建隔离 worktree，`pane run` + `pane wait-output` 跑测试。

三个诚实限制：

1. **无编排层**：任务图、账本、自动重试、自动合并、评审门禁自动触发，都要主 Agent 用原语自己写循环，或写 plugin（事件钩子 + action）。它解决执行层，不解决交付规则。
2. **状态检测是屏幕识别，可能误判**：官方明确 `idle` 不代表 approval 对话框被识别；Antigravity/Grok 可能 idle 但后台任务仍在跑。与 sc 的 `prompt_stalled` 同类风险。
3. **中断恢复有限**：detach/reattach 进程不丢；server 重启后进程丢失，需 native session restore（integration），本机 integration 当前全部未安装。

本机现状：herdr 0.9.5 已装且在用，IssueHub 工作区已有 omp/pi/codex 三个 agent pane；当前 SDLC 会话不在 herdr 内（`HERDR_ENV` 未设置）。

阶段性判断：herdr 的同步阻塞等待模型天然规避了 sc 的跨 worktree 断点，且 token 机制更好；但交付闭环仍需主 Agent 自己编排，且屏幕识别误判与中断恢复两个风险仍需实测。

## 4. 当前结论

### 4.1 对原方案的结论

需要重新裁剪，而非直接实施原 v0。

| 原方案内容 | 判断 |
|---|---|
| 任务说明、验收标准、结果摘要 | 保留 |
| worktree 隔离 | 保留，服务于并行开发和独立评审 |
| 跨模型评审、修复后复审 | 必须纳入最小方案，不能延后 |
| 自动测试、集成、失败后继续处理 | 必须纳入最小方案 |
| 状态持久化与中断恢复 | 需要，具体存储方案待定 |
| 主 Agent token 优先、固定摘要硬上限 | 降为优化项，不能妨碍判断 |
| 多机、看板镜像、四家适配器 | 暂不做 |
| Beads + SQLite + 自建 daemon | 尚未证明必要，先确认现有能力缺口 |

### 4.2 能力验证现状

| 能力 | 状态 |
|---|---|
| 跨 provider 启动与结果读取 | 已证实 |
| 同 worktree 聊天 Agent 完成通知唤醒主会话 | 已证实 |
| 文本协作的返工与复审闭环 | 已证实 |
| 真实开发、独立评审、集成、合入功能集成分支 | 已证实 |
| 跨 worktree 任务完成后自动续接（无人值守） | 未通过，断点已定位，待解决 |
| 真实代码评审发现问题后的修复与复审 | 未验证 |
| 合并冲突恢复 | 未验证 |
| 应用重启 / 会话中断后的恢复 | 未验证 |
| 多轮长期稳定性 | 未验证 |

### 4.3 适合的交付流程（目标形态）

```
用户确认需求与方案
        ↓
主 Agent 建立功能集成分支、拆任务与验收标准
        ↓
开发 Agent 在独立 worktree 实现
        ↓
另一模型评审明确的代码版本
        ↓
发现问题 → 修复 → 复审
        ↓
合入功能集成分支，运行集成检查
        ↓
阶段整体评审 → 必要时继续修复与验证
        ↓
交付代码、验证证据、调整记录及遗留问题
```

三条运行规则：

1. 正常失败不等用户处理（测试失败、成立的评审意见、常规集成冲突由主 Agent 组织解决）。
2. 调整记录随执行更新（调整了什么、为什么、对需求与架构的影响、对应提交与验证结果）。
3. 不能无限循环也不能假装完成（连续修复无进展或无法同时满足需求与架构时，保存现场并交付阻塞说明）。

最终交付四样：功能集成分支及最终提交、需求验收与测试结果、跨模型评审与问题处理记录、方案调整记录与遗留事项。

### 4.4 选型结论

执行基础设施优先复用现有工具，不先建设原方案 v0。候选排序随调研更新：

- **herdr**：同步阻塞等待模型规避 sc 的跨 worktree 断点，token 机制更好，本机已装且在用，作为下一轮实测的首选。
- **super.engineering**：协作链路已验证，但跨 worktree 无人值守断点未解决，token 消耗偏高，降为次选。
- Orchestrator.inc、Gas Town：有明确理由时再验证。
- 只有实验暴露出现有工具无法覆盖、且反复发生的问题，才值得为它补代码。

## 5. 待办事项

按优先级排序：

1. **用 herdr 复现实测同步阻塞闭环（下一步）**：在 herdr 内用 `agent prompt --wait` 派发开发、阻塞等待、读结果，验证跨模型评审与返工能否在一个会话内推进，重点观察屏幕识别是否误判完成。
2. **对比 herdr 与 sc 的实际 token 消耗**：同一小任务分别走两套工具，量化差距，确认 herdr 是否真省 token。
3. **验证真实代码的评审返工闭环**：评审发现问题 → 自动修复 → 复审，记录处理结果。
4. **验证合并冲突与常规失败的自愈**：主 Agent 组织解决，不把常规失败直接丢给用户。
5. **验证中断恢复**：会话结束、herdr server 重启后的恢复能力（integration 是否需安装），不能把中断误报为成功。
6. **记录交付所需四样证据**：在真实功能上走通后，确认代码、验收、评审记录、调整记录齐全。
7. **在明确理由出现前，不建设原方案 v0**（不建 Beads/SQLite/daemon/orch）。
