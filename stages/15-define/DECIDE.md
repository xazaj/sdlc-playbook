# 需求与规格阶段：写法与评审选型

## 要回答的问题

- 这个需求要写到多细：口头确认、结构化条目、PRD，还是变更级规格？
- 需求条目用什么句式写，才能被验证、被机检地评审？
- 一份写好的规格按什么标准评审、谁来评？
- 交给 agent 执行时，规格的角色有何不同？

「这次改动要不要先写规格」是开发流程判定，见 `stages/30-coding/DECIDE.md`；本矩阵只管写到多细、按什么句式、谁来审。

## 判断依据

四个维度按权重排序：

1. **涉众数量**：几个人要读过并认同这份需求。规格的首要功能是对齐，只有自己看的需求投入回报最低。
2. **需求确定性**：现在能否说清目的、约束与成功标准。说不清时先澄清，不要先挑模板。
3. **执行方式**：是否交给 agent 长时间自主执行。上下文会被压缩和替换，文件是唯一不丢的锚点。
4. **改动可逆性**：需求对应的改动错了能不能便宜地回滚。

第一条权重最高。涉众只有一个时，后面三条再严重，也只需要轻量的规格形态加好的句式。

## 选型矩阵

| 规格形态 | 适用条件 | 代价 | 反模式（不应使用的场合） |
|---|---|---|---|
| **口头确认（不写）** | 单人涉众；范围小；错误立刻可见 | 无留痕，上下文压缩后即丢失，事后无法对账 | 交给 agent 长时间执行；多涉众；涉及资金、权限、数据迁移 |
| **结构化条目（EARS 句式）** | 条目会被验证或评审；需要可对账的需求清单 | 句式学习成本一次性 | 三五条以内的琐碎需求，为句式而句式；探针问题与内部备忘 |
| **产品级 PRD** | 多涉众对齐；长期产品要划定范围（MoSCoW、MVP 边界、user story 与验收标准） | 写与维护成本高，会随产品演进漂移 | 一次性脚本；内部小工具；需求已谈妥只差落纸 |
| **变更级规格 + 实现计划** | 跨模块改动；交给 agent 自主执行；错误代价高 | 规格比代码先过期时会变成误导 | 已明确知道改哪几行的小修改；可行性未定（先做探针） |

四种形态从轻到重。任何时刻都可以降级退回轻的一档；升级要有信号触发，不要预支。

## 推荐路径

默认按涉众数量决定：

- 只有自己：口头确认；条目超过一屏再改用 EARS 条目
- 多涉众：协作写 PRD，条目用 EARS 句式
- 交给 agent 长时间执行：变更级规格 + EARS 句式，写完转实现计划

出现以下信号时改变默认：

| 信号 | 改走 |
|---|---|
| 想法说不清目的与成功标准 | 先走 brainstorming 澄清，不要先挑模板 |
| 输入是一大堆 URS/BRD | 先摄入拆解出冲突与高风险决策点，再动笔 |
| 规格或 PRD 写完要开工 | 先按 EARS 自检句式，再上评审四件套 |
| vibe 出来的 demo 要移交研发 | 逆向回填需求，不要让研发读代码猜意图 |
| 有人问「要不要先写规格」 | 转到 `stages/30-coding/DECIDE.md`，那是流程判定 |

## 交给 agent 执行时的差异

**规格的价值被放大，形态的重量被压扁。** 上下文压缩后口头交代的需求不可靠，文件是唯一锚点；同时 agent 写文档的边际成本远低于人，PRD 与变更级规格的「太费人力」论据要打折扣。但阅读与维护成本没有消失，重量该减还是要减。

**句式约束变得可执行。** EARS 五种句式对人是写作规范，对 agent 是可机检的语法：不符合任何一种句式的条目可以被自动拒收。评审因此从「我觉得这条不清楚」变成「这条不符合任何一种句式」。

**评审可以自动化，品味不能。** autoplan 能把四个视角的评审串起来无人值守跑完，每个发现带置信度与证据引用；但「哪个方案更好」一类的品味决策仍会浮出要求人批准。全盘接受自动评审结论与不评审一样危险。

**第一个读者应该是无上下文的 agent。** 作者与协作者共享语境，看不出盲区。用一个只拿到文档本身的子代理当第一个读者，是成本最低的盲区检测。

## 常见误判

- **把「要不要写规格」与「写到多细」混为一谈。** 前者是编码阶段的流程判定（TDD/SDD/直接实现/探针），本阶段只回答形态、句式与评审。为回答一个问题读两份矩阵是正常的，它们本来就是两个决策。
- **为三五条需求的小改动上 PRD 流程。** 目录、涉众、背景、里程碑全套下来，规格比改动本身长，且写完即作废。
- **需求里写实现而非行为。** 「用 Redis 缓存会话」是方案；「When 用户重新打开页面，系统应在 3 秒内恢复上次的列表」才是需求。写死了实现，评审就被锁死在别人的技术选型上。
- **评审没有可检验的标准。** 「我觉得不清楚」式的评审意见既不能通过也不能关闭。先有 EARS 句式这样的客观标准，评审发现才是可执行条目。
