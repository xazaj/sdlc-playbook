# 设计阶段：设计系统与视觉方案选型

## 要回答的问题

- 这个界面应使用现成组件库、沿用已有规范，还是由 AI 直接生成视觉？
- 是否需要建立 token 体系？达到什么规模才值得？
- 交给 agent 做 UI 时，如何避免生成结果"像模板"？

## 判断依据

按权重排序：

1. **存续周期**：这个界面会使用多久。一次演示，还是要演进两年。
2. **界面规模**：一到三屏，还是几十屏。
3. **品牌辨识度要求**：是否需要让人看出"这是你们的产品"。
4. **是否多品牌或多主题**：同一套界面要出几套皮肤。

第一个维度权重最高。存续周期短的界面，任何设计系统投入都收不回。

## 选型矩阵

| 方案 | 适用条件 | 代价 | 反模式（不应使用的场合） |
|---|---|---|---|
| **AI 直接生成视觉** | 一次性演示、原型、内部工具；一到三屏 | 没有一致性保证，屏数一多必然散架 | 长期演进的产品；超过 5 屏的界面 |
| **现成组件库**（shadcn/ui、Radix + Tailwind、Material 3） | 中大型产品；没有专职设计师；要快且不能难看 | 默认主题辨识度低，容易"看起来像所有其他产品" | 需要强品牌表达的营销页与落地页 |
| **沿用产品已有规范** | 在已有设计系统的产品中新增界面 | 受限于既有规范的表达力 | 既有规范本身很差，而这次正是重做的机会 |
| **自建 token 体系**（DTCG 三层：primitive、semantic、component） | 多品牌或多主题；设计与开发分离协作；长期演进 | 建设与维护成本高，小项目收不回 | 单品牌的内部工具；确定的一次性项目 |

## 推荐路径

默认按存续周期决定：

- 一次性或演示：AI 直接生成
- 长期、单品牌：现成组件库，加一层语义 token 覆盖品牌色与排版
- 多品牌或多主题：DTCG 三层 token

出现以下信号时改变默认：

| 信号 | 改走 |
|---|---|
| 要有品牌辨识度 | 现成组件库，但必须定制排版与色彩，不用默认主题 |
| 产品已有设计规范 | 沿用，不另起炉灶 |
| 会超过 20 屏 | 无论周期长短都要有 token 层，否则改一次主色要改几十处 |
| 设计师会参与 | 提前建 token 体系，它是设计与开发的交接界面 |

## 交给 agent 执行时的差异

**AI 生成 UI 的默认产物有强烈的模板感**：紫色渐变、圆角卡片、居中英雄区、三栏特性网格。这不是模型能力问题，而是缺少约束。没有给定方向时，它会收敛到训练数据中最常见的那一种。

解法不是每次口头描述，而是提供一份显式的设计约束文件：YAML frontmatter 存 token（色彩、字体、间距、圆角），正文写意图（应有什么感觉、什么绝对不要）。口头描述会在上下文压缩后丢失，文件不会。

**token 的语义层对 agent 尤其重要。** 有 `semantic` 层时，agent 改品牌色只改一处；没有时，它会在几十个文件中硬编码 hex 值，且下次改动会漏掉一半。三层 token 原本是为人减负，在 agent 时代还承担约束改动半径的作用，价值因此被放大。

**设计评审不能完全交给 agent。** 它能可靠地检查对比度、间距一致性、语义标签、响应式断点；它判断不了"这个界面好不好看""有没有辨识度"。前者可以放心交出，后者必须由人来看。

## 常见误判

- **为内部工具自建 token 体系。** 建设成本永远收不回，用现成组件库的默认主题即可。
- **用 AI 生成长期演进产品的视觉。** 前三屏惊艳，第十屏开始必然失控，因为每一屏都是独立生成的，没有共享约束。
- **以为换了组件库就有了设计系统。** 组件库是零件，设计系统是"怎么用这些零件"的约定。只装了 shadcn 不等于有设计系统。
- **让 agent 做最终视觉评审。** 它会给出一份看起来很专业的检查清单，但清单上没有"这看起来很廉价"这一条。
