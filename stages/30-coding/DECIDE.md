# 编码阶段：开发流程怎么选

## 要回答的问题

- 这次改动该走测试先行（TDD）、规格先行（SDD）、还是直接实现？
- 什么时候该先做一个探针（spike）而不是直接动手？
- 交给 agent 自主执行时，流程选择有什么不同？

## 判断依据

三个轴决定答案，按重要性排序：

1. **正确性验证成本** —— 写错了，多久会被发现？立刻（UI 错位、脚本报错）还是很久以后（金额算错、并发竞态、数据被悄悄写坏）？
2. **需求确定性** —— 你现在能说清楚"做完是什么样"吗？
3. **改动范围** —— 几行，还是跨三个以上模块？

第一个轴权重最高。**验证成本高的地方，流程投入才有回报。**

## 选型矩阵

| 流程 | 适用条件 | 代价 | 反模式（别在这些地方用） |
|---|---|---|---|
| **TDD 测试先行** | 逻辑分支多；有明确的输入输出契约；错误要很久才会暴露；要重构既有代码 | 前期慢；测试本身成为需要长期维护的资产 | UI 布局与视觉细节；一次性脚本；还不知道要什么的探索阶段 |
| **SDD 规格先行** | 需求模糊或涉及多方确认；改动跨多个模块；要交给 agent 长时间自主执行 | 写规格的时间在小改动上收不回来；规格会随代码漂移 | 单文件小修改；你已经确切知道要改哪几行 |
| **直接实现** | 改动范围明确且小；有现成的相似代码可照着写；错了立刻能发现、回滚成本低 | 不留下任何可回归的资产 | 涉及钱、权限、数据迁移的逻辑；没有相似代码可参照的新领域 |
| **探针先行 spike** | 可行性未知；第三方库或接口的真实行为不确定 | 产出是答案不是代码，必须明确扔掉 | 你其实已经知道能做，只是懒得动手 |

## 推荐路径

**默认按验证成本决定：**

- 错了会立刻被发现 → **直接实现**
- 错了要过很久才发现 → **TDD**

**以下信号出现时，改变默认：**

| 信号 | 改走 |
|---|---|
| "我不确定这个库/接口能不能做到" | 先 spike，拿到答案再选流程 |
| "这会动到三个以上模块" | 先 SDD 写规格，再按模块分别选流程 |
| "这段代码半年后还会有人改" | TDD —— 测试是唯一不会过期的文档 |
| "需求还要跟人对齐" | SDD —— 规格是对齐的载体，代码不是 |

## 交给 agent 执行时的差异

这是 2026 年最重要的变化，与人类独自编码时的权衡不同：

**TDD 的价值被放大。** 测试是 agent 唯一可靠的自我验证信号。没有测试，agent 会声称"已完成"，但你无法低成本地确认它是否真的完成 —— 而它自己也无法确认。有测试时，"跑通了"是事实；没测试时，"跑通了"是它的主观判断。

**SDD 的价值同样被放大。** agent 长时间自主执行时，上下文会被压缩、被替换。一份写在文件里的规格是唯一不随上下文丢失的锚点。口头交代的需求在第三次压缩后就不可靠了。

**直接实现的适用范围收窄。** 它依赖"错了立刻能发现"，而 agent 的错误往往是**看起来对的**：命名合理、结构工整、逻辑错误。人类的直接实现有肌肉记忆兜底，agent 没有。

**实操结论：** 让 agent 做验证成本高的改动时，即使人类自己做会选直接实现，也应该要求它先写测试。

## 常见误判

- **给 UI 布局写 TDD** —— 测试断言的是 DOM 结构或像素值，改一次样式就红一次，维护成本远超收益。UI 该用的是视觉回归或人眼检查。
- **给一次性迁移脚本写规格** —— 规格比脚本还长，且写完就作废。
- **让 agent 在没有测试的情况下重构** —— 重构的定义是"行为不变地改结构"，没有测试就无法验证"行为不变"这半句，那就不是重构，是重写。
- **先写测试再想清楚要什么** —— TDD 要求你先知道正确的输出是什么。需求不清时它不是 TDD，是在用测试的形式做探索，两边都做不好。这种情况该走 spike 或 SDD。
