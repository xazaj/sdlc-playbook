# 编码阶段：开发流程选型

## 要回答的问题

- 这次改动应采用测试先行（TDD）、规格先行（SDD），还是直接实现？
- 何时应先做探针（spike），而非直接动手？
- 交给 agent 自主执行时，流程选择有何不同？

## 判断依据

三个维度决定答案，按权重排序：

1. **正确性验证成本**：写错后多久会被发现。是立刻发现（UI 错位、脚本报错），还是很久以后（金额算错、并发竞态、数据被静默写坏）。
2. **需求确定性**：现在能否说清"做完是什么样"。
3. **改动范围**：几行代码，还是跨三个以上模块。

第一个维度权重最高。验证成本高的地方，流程投入才有回报。

## 选型矩阵

| 流程 | 适用条件 | 代价 | 反模式（不应使用的场合） |
|---|---|---|---|
| **测试先行（TDD）** | 逻辑分支多；有明确的输入输出契约；错误暴露周期长；重构既有代码 | 前期慢；测试成为需长期维护的资产 | UI 布局与视觉细节；一次性脚本；尚不清楚目标的探索阶段 |
| **规格先行（SDD）** | 需求模糊或需多方确认；改动跨多个模块；交给 agent 长时间自主执行 | 小改动上写规格的时间收不回；规格会随代码漂移 | 单文件小修改；已明确知道要改哪几行 |
| **直接实现** | 范围明确且小；有相似代码可参照；错误立刻可见且回滚成本低 | 不留下任何可回归的资产 | 涉及资金、权限、数据迁移的逻辑；没有相似代码可参照的新领域 |
| **探针先行（spike）** | 可行性未知；第三方库或接口的真实行为不确定 | 产出是答案而非代码，必须明确丢弃 | 已知可行，只是不想动手 |

## 推荐路径

默认按验证成本决定：

- 错误立刻可见：直接实现
- 错误很久后才暴露：TDD

出现以下信号时改变默认：

| 信号 | 改走 |
|---|---|
| 不确定某个库或接口能否做到 | 先做 spike，得到答案后再选流程 |
| 改动涉及三个以上模块 | 先按 SDD 写规格，再逐模块选择流程 |
| 这段代码半年后仍会有人修改 | TDD。测试是唯一不会过期的文档 |
| 需求仍需与人对齐 | SDD。规格是对齐的载体，代码不是 |
| 同一问题反复出现，或补丁与变通方案不断堆积 | 先跑架构优先预检（见落地资产）定位归属层与根因，再回来选流程 |

## 交给 agent 执行时的差异

agent 自主执行时的权衡与人工编码不同，这是 2026 年最重要的变化。

**TDD 的价值被放大。** 测试是 agent 唯一可靠的自我验证信号。没有测试时，agent 会声称"已完成"，但用户无法低成本地确认，agent 自身也无法确认。有测试时，"跑通"是事实；没有测试时，"跑通"只是它的主观判断。

**SDD 的价值同样被放大。** agent 长时间自主执行时，上下文会被压缩和替换。写在文件中的规格是唯一不随上下文丢失的锚点，口头交代的需求在第三次压缩后即不可靠。

**直接实现的适用范围收窄。** 直接实现依赖"错误立刻可见"，而 agent 的错误往往看起来是对的：命名合理、结构工整、逻辑错误。人工直接实现有经验兜底，agent 没有。

**实操结论：** 让 agent 做验证成本高的改动时，即使人工会选择直接实现，也应要求它先写测试。

## 常见误判

- **为 UI 布局写 TDD。** 测试断言的是 DOM 结构或像素值，每改一次样式就失败一次，维护成本远超收益。UI 应采用视觉回归或人工检查。
- **为一次性迁移脚本写规格。** 规格比脚本还长，且写完即作废。
- **让 agent 在没有测试的情况下重构。** 重构的定义是"行为不变地修改结构"。没有测试就无法验证"行为不变"，那不是重构，而是重写。
- **需求未清就先写测试。** TDD 要求事先知道正确输出。需求不清时写测试不是 TDD，而是以测试的形式做探索，两者都做不好。此时应走 spike 或 SDD。
